An external audit of this repository against the paper it re-implements, together
with a work list. It was produced by re-deriving every checkable claim from the
PDF and from the real FD001 files. Nothing in it was quoted from memory, and no
file in the project was modified while it was made.

It is written to be handed to a session that starts cold. If you are that
session:

1. Read `CLAUDE.md` first. Everything below is subordinate to it. In particular
   rule 2 (never report a number you have not computed), rule 3 (one seed is not

   rule 6 (correct errors plainly) and rule 8 (do not commit without being
   asked) all bear directly on this work list.
2. Read Part 1 to see what has already been verified, so you do not spend the
   session re-deriving it. Every check in Part 1 is reproducible; the commands

3. Work Part 2 in order. Items 1-3 and 7-9 are mechanical. Items 4-6 need a
   decision from the author first — they are marked **DECISION** and Part 3 sets
   out the options.
4. Do not commit. Report what changed and stop.

## Item 5 — **DECISION** — rewrite A-21's "how much it matters"

`docs/ASSUMPTIONS.md:905-931`. Two claims in it no longer hold with the varying
split:

- symmetric is no longer ahead on the mean. Row is **lower**: 14.007 against
  14.130.
- "The row form's variance across seeds is **6.7 times** the symmetric form's"
  is now **1.13x**.

The 6.7x was an artefact of holding the split fixed. With the split fixed only
initialisation and batch order varied, and the row form happened to be the more
sensitive of the two; once split variance enters, it dominates both forms
equally. That is a good explanation and worth writing down rather than quietly
deleting, per rule 6.

**A-21's actual conclusion is strengthened, not weakened.** "The choice does not
materially change what the model achieves" now rests on p = 0.58 rather than
p = 0.20, and on two orderings that disagree — which is exactly what "no real
difference" looks like. What has to go is the *stability* half of the
justification and the closing sentence "it is the more stable of the two",
leaving the Kipf-and-Welling citation argument, which was always the stronger
one.

Under option 4(b) this item still applies: the old numbers must be labelled
`--fixed-split`, and the 6.7x must be stated as a property of the fixed split
rather than of the normalisation.

# Part 3 — What the author has to decide

Three questions. Everything else on the list is mechanical.

**Q1. Which split do the published numbers use?**
Adopt the varying-split figures (option 4a), or keep the fixed-split ones and
label them (option 4b). Rule 3's own wording favours 4a. If 4b, the fixed-split
runs must be regenerated with `--fixed-split`, since they no longer exist in the
tree.

**Q2. Should the headline comparison be the capped or the uncapped figure?**
The capped figure is the one the architecture justifies (A-02's argument is
sound). The uncapped figure is the one comparable with the literature. The
honest presentation is probably both, with the 1.76-cycle difference stated —
but that is a judgement about how to frame the result, not something to settle
by fiat.

**Q3. How many seeds?**
Everything above is five seeds, which is what rule 3 requires. The A-21
comparison is now the only one where the answer is "no detectable difference"
with a p-value that would move under more seeds (p = 0.58). If A-21 is going to
carry weight in the thesis, ten seeds would settle it more firmly. A five-seed
run takes about eight minutes on CPU, so ten seeds of both forms is roughly half
an hour.

## Reading a figure off the paper

The method used for A-01, which item 9 asks to be preserved: render the page
with `pypdfium2` at scale 12; find the axis spine as the column with the most
near-black pixels in the left third; find the tick rows as runs where dark
pixels sit immediately left of the spine; fit a line from tick row to axis
value and report the residual; then take the median row of the coloured pixels
in the region of interest and map it through that fit. Report the residual and
the printed line thickness alongside the value, so the reader can see the
precision. Never read a value off a page thumbnail.
